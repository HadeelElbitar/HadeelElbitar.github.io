How Readoactive is built

From a shared video to books on your shelf: one box, one contract behind every API and AI tool, and every model call accounted for.

Readoactive is the book tracker I built for people who find their next read on BookTok and Reels. You share a video, and it finds every book in it, matches each one to a real edition, and keeps track of series, narrators and what you can borrow free from your library.

I'm the only engineer, so every architectural decision had to pass one test: can one person run this, change it every day and sleep at night? Here's the whole system. Tap any part to see what it does, or follow a single video through it.

The production system. Everything except the clients, Claude, Whisper and the data sources runs on a single Ubuntu server.

One box, on purpose

The whole thing runs on one server: Caddy in front, the API, a background worker, and Postgres. No Kubernetes, no message broker, no Redis. Background jobs are rows in a Postgres table, so a capture that's halfway done survives a restart, the API can run as several processes, and there's one less system to keep alive.

That isn't a lack of ambition. It's the same call I'd make for a team: pick the smallest architecture that meets the reliability bar, and make it easy to leave. Nothing is tied to the host. Moving means running the setup script on a new machine, restoring last night's dump and pointing the domain. Backups run nightly, with a second copy kept offsite.

One contract, three front doors

Every action in the product, from "add this book" to "join this club", is declared once in a single contract: its inputs and outputs, the OAuth scopes it needs, whether it's safe to retry, whether it runs as a background job, and whether AI assistants may call it. From that contract the system generates the HTTP routes the app uses and the tool definitions for the MCP server that Claude and other assistants use.

That's why the AI integration came almost for free, and why it's safe. An assistant signs in through the same OAuth 2.1 server as the app (dynamic client registration and PKCE), gets scoped, revocable tokens, and can't reach anything the contract doesn't allow. Destructive operations, like deleting a list or undoing an import, are deliberately left out of MCP. With fifteen years in identity, I wasn't going to bolt auth on later.

Paying for the model only when it helps

Model calls are the main running cost, so the capture pipeline is built to look as little as it can. It reads the caption while the video downloads, then the transcript. Frames are sampled in a background thread at the same time, so they're ready if needed, but the expensive vision pass only runs when the text leaves doubt. A quick, cheap look at eight frames settles most of the borderline cases. On videos where every book is said out loud, skipping frames cuts the cost by about 90%.

    What runs for three kinds of video. The rules come straight from the pipeline's own decision code.

    Two more pieces keep the spending honest. Every call to Claude goes through one model gate, which records what it was for, how many tokens it used, and which reader and job it served, so the admin page shows exactly where the money goes. When the model is down or out of credit, the gate remembers it, shows a banner, sends one email, and pauses background work for an hour instead of failing a thousand times. Captures still try, and they're queued and retried rather than lost.

    Second, a capture corpus keeps everything a capture already paid for: the transcript, every raw model response, the comments and the sampled frames. When I improve extraction, I can rerun the new logic over stored results instead of paying for the same videos again.

    Shipping every day without a team to catch me

    A push to main deploys, but only through a gate that refuses to ship anything it can't vouch for:

    • The full test suite, 1,220 tests, run in parallel.
    • A replay of 320 real library imports against a recorded catalog, which fails if any row would match a different book than it did before. The nightly run does the same over every stored import and emails me when a count moves.
    • A browser canary that drives 41 screens of the real app and fails on any broken layout.

    The gate looks at what changed and skips the checks that change can't affect, so a copy edit ships in minutes and a matcher change gets the full treatment. Deploys run one at a time, and the server is restarted through socket activation, so requests wait a moment instead of failing. The same budget rules bind the AI coding agents I work with: tests replay stored model results by default, and fresh model calls are capped per day.

    The bigger takeaway

    • Declare things once. One contract gave me the API, the AI tools and authorization rules that can't drift apart.
    • Make the expensive path the exception. The cheapest signal runs first, and each costlier step has to earn its place.
    • Never pay twice for the same answer. Keep what you've already bought, and design so you can replay it.
    • Let the gate say no. When nobody is reviewing your pull requests, the deploy pipeline has to be the reviewer.

    None of this is specific to books. It's how I'd want any platform to work: small enough to understand, strict about access, careful with money, and safe to change on a Friday.
