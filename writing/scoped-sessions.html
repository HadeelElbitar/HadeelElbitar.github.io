A checkout login shouldn't be able to send money

Why we had to rethink what being logged in actually means.

Hadeel Elbitar·8 min read

Most apps have a pretty simple idea of authentication. You log in, we know who you are, and you get access to your account. Simple enough, right?

Except that model starts falling apart the moment you let people log in from places other than your own app.

We ran into exactly this problem when we started supporting checkout flows where someone could pay with our app directly from a merchant's website. Think about it. You're shopping online, you choose to pay with a payments app, and you log in through a browser to approve the purchase. All you really need to do is approve that one transaction.

But traditionally, the session you'd get after logging in was the same kind of session you'd get on your own phone. One that could send money, manage bank accounts, change security settings, or reach pretty much anything else your account supports. That's a lot of power to hand to a browser session that only needed to approve a checkout.

That's the problem we set out to solve.

Being authenticated shouldn't mean having access to everything

The way I think about it, authentication and authorization answer two very different questions.

AuthenticationWho are you?
AuthorizationWhat are you allowed to do?

We've been pretty good at separating the two for third-party applications. OAuth scopes exist for exactly this reason: you give an external app access to your account, but only to the specific things it needs.

For some reason, we tend to forget that distinction with our own applications. It's our app, our login, our API. Why wouldn't we trust it?

Because not every login happens in the same context. A session created on your personal phone, inside an app you use every day, is very different from one created in a browser during checkout on a merchant's website, even if it's the exact same person logging in.

If that checkout session gets stolen, phished or left open somewhere, the damage it can do should be limited to what it was created for.

A checkout session should be able to complete checkout. Not send money to a stranger. Not link a new bank account. Not buy crypto.

A reasonable expectation, but not one traditional first-party sessions enforce.

Enter Scoped Sessions

The idea was straightforward: instead of giving every login full access, give each session only the permissions it actually needs. We called this Scoped Sessions.

It's similar to OAuth scopes, with one important difference. We didn't want every client deciding which permissions to request. That would add complexity, make auditing harder, and let clients ask for access they shouldn't have. Instead, we introduced predefined tiers. The entry point chooses a tier, and the server decides exactly which permissions belong to it.

For example, a checkout session might have permission to:

  • Read the account information needed for checkout.
  • Review and approve the current purchase.
  • Confirm a passcode if an additional security check is required.

And that's it. It doesn't get to send peer-to-peer payments, register passkeys, or reach unrelated account features.

Same user, same account. The tier alone changes what an API will accept. Permission and tier names here are illustrative.

The API endpoints enforce those boundaries themselves. Each endpoint explicitly declares which permissions it accepts from scoped sessions. And here's an important design decision: if an endpoint hasn't opted into accepting scoped sessions, it requires a full session. No declaration means no scoped access.

Scoped sessions are also shorter-lived. A checkout session might last days rather than the months available to a full app session, and more temporary flows get sessions that last only minutes.

And if someone needs to do something outside their session's permissions? They log in again to get a full session. We deliberately didn't allow upgrading an existing scoped session into a more powerful one.

Same user. Same account. Different session. Different permissions.

Nothing particularly revolutionary about the concept. The interesting part was getting it to work in an ecosystem that had never needed to think about sessions this way.

The easy part was designing it. The hard part was everything else.

When you introduce a new permission model into an existing system, you're not starting from scratch. You're dealing with years of assumptions baked into hundreds of endpoints across dozens of services, all built around the idea that a valid session is a full session. That was the real challenge.

1. Secure by default also means broken by default

We had two possible approaches. We could let scoped sessions access everything by default, then gradually restrict the endpoints that shouldn't accept them. Or we could reject scoped sessions everywhere by default, then explicitly allow them only where needed.

We chose the second. From a security perspective it was the obvious choice: if we missed an endpoint, access would be denied instead of accidentally granted. From a product perspective, though, every endpoint we missed could break a legitimate flow.

And of course, we missed things.

One of the first issues showed up during checkout. Depending on the account's security settings, the user might need to confirm their passcode before approving a payment. The checkout session had permission to approve the payment, but the passcode confirmation endpoint hadn't been configured to accept it. So the checkout flow got stuck.

The session was doing exactly what we'd designed it to do, and so was the API, rejecting access it hadn't been told to allow. We just hadn't accounted for that dependency. The fix was simple: add a passcode confirmation permission to the checkout tier and update the endpoint to accept it.

But it highlighted something important. A permission model isn't just about identifying the main action. You have to understand every supporting action that makes the flow work, and in a system with hundreds of APIs those dependencies aren't always obvious.

2. Backwards compatibility has a sense of humor

Another fun problem came from an existing API contract. Before Scoped Sessions, an empty list of required permissions meant the caller needed full access. That behavior had been around for a while, and existing clients depended on it.

Introduce scopes, and suddenly an empty list is ambiguous. Does it mean no permissions are required? That the endpoint accepts any session? Or that full access is required? Those interpretations are very different, and getting one wrong could turn into a security issue. We couldn't change what the empty list meant without breaking existing behavior.

So instead of letting an empty array carry all that meaning, we made the authorization decision explicit in our internal model, with three possible states:

  • Skip the check, when authentication requirements are handled elsewhere.
  • Require full access, which preserves the existing behavior.
  • Require specific permissions, for endpoints that support scoped sessions.

We only translate that back into the older API format at the boundary. It's a small implementation detail, but exactly the kind that becomes surprisingly important when you're evolving security infrastructure.

Sometimes the hardest part isn't implementing the new behavior. It's preserving every old behavior people forgot was a contract.

3. We rolled out session issuance, not enforcement

This is another decision I think worked particularly well. We didn't put authorization enforcement behind a feature flag.

That might sound counterintuitive. Usually, when you're rolling out something this invasive, you want to be able to switch it off quickly. But flagging security enforcement brings its own problems: you now have multiple authorization behaviors, and you have to reason about what happens whenever the flag changes.

Instead, enforcement was always on. What we controlled was whether the system issued scoped sessions in the first place. If no scoped sessions are being issued, full sessions keep working exactly as before. As we enabled scoped session issuance for specific flows, the enforcement was already there.

Any rejection was a real rejection, not something that depended on whether a flag happened to be on. That made the authorization logic much easier to reason about, while still giving us control over the rollout.

4. Checkout was only the beginning

Once the model worked for checkout, other use cases appeared. Different entry points needed different levels of access. Some needed sessions that lasted days, others only minutes. Some needed a handful of permissions, others a slightly broader set.

So the model grew. Each new entry point got a predefined tier, a fixed set of permissions and an appropriate session lifetime. Across the API surface, hundreds of endpoints in dozens of services eventually needed explicit permission declarations.

The individual changes weren't necessarily complicated. The challenge was understanding what each endpoint did, how it was used, and which flows legitimately needed it. That's hard to automate away, because the question isn't just technical. It's a product and security question: should a session created in this context be allowed to do this? Someone has to understand the implications well enough to answer it.

What I'd do the same way again

  • Treat first-party applications as untrusted contexts too. Being first-party doesn't mean every session deserves full access. The context a session was created in matters as much as who wrote the client.
  • Use predefined permission tiers when the use cases are known. Letting clients assemble arbitrary scope lists is flexible, but flexibility isn't always helpful in security-sensitive systems. Fixed tiers are easier to understand, review and audit.
  • Default to denying access, even when it's inconvenient. You're going to miss endpoints, break flows and discover dependencies nobody remembered existed. I'd much rather those mistakes show up as bugs to fix than as permissions we accidentally granted.
  • Never overload an empty value with security meaning. If an empty list means something important, make that explicit in the type system. Don't make the next engineer guess whether [] means nothing, everything or something in between.
  • Don't pretend you have step-up authentication if you don't. It would be nice to let someone elevate a scoped session after an extra verification step. But unless you've actually designed and secured that mechanism, a fresh full login is simpler and safer. Not the smoothest experience, admittedly, but one with much clearer security boundaries.

The bigger takeaway

What I find interesting about this project is that the core idea was almost boring. Apply least privilege to sessions. Give each login only the permissions it needs. That's a principle we've been talking about forever.

Applying it to an established system was a different story. It meant revisiting assumptions made years earlier, understanding dependencies across hundreds of APIs, dealing with backwards compatibility, and accepting that a secure default would sometimes break legitimate experiences.

I think that's the part that gets overlooked in a lot of engineering discussions. Coming up with a better model is often the easy part. Getting an entire existing system to consistently respect it, without creating new security problems along the way, is where the actual engineering happens.

A login should prove who you are. It shouldn't automatically hand you the keys to everything.
